# تدقيق Diskoko الشامل وخارطة 440 ميزة

## الخلاصة التنفيذية

يملك Diskoko أساساً حقيقياً لتسجيل الدخول عبر Discord، وتحديد السيرفرات القابلة للإدارة، وتثبيت البوت، وقراءة القنوات والرتب، وإنشاء موارد ناقصة من بعض القوالب. لكن المنتج الحالي يجمع بين محرر محلي في `localStorage`، ومركز Studio تشغيلي، وصفحات تسويق، من دون مصدر حقيقة موحد يربط التصميم بالسيرفر وحالة النشر.

الفجوة الأهم ليست عدد الأزرار، بل **الفصل بين المعاينة والتنفيذ**. يجب أن يرى المستخدم ما سيتغير، وما الصلاحيات المطلوبة، وما نتيجة كل عملية، قبل أن يكتب النظام إلى Discord. كما يجب ألا تعرض الواجهة Bot أو AI أو أتمتة باعتبارها جاهزة ما لم توجد handlers وخدمات runtime فعلية.

## الوضع الحالي المختصر

| المجال | الموجود | الفجوة الرئيسية | الأولوية |
|---|---|---|---|
| الواجهة الرئيسية | صفحة تسويق، OAuth، رابط مجتمع، باقات | CTA غير موحد، الباقات لا تقود إلى اشتراك فعلي، محرر محلي مخفي داخل المسار | P0 |
| الحساب | خطة، سيرفرات، مرتبط/غير مرتبط، إعدادات | ربط Google بـDiscord، إنفاذ السعة، سجل تدقيق، تشخيص صلاحيات | P0/P1 |
| Studio | ربط Guild، قوالب، معاينة، Change Sets | واجهات متنافسة، مصدر حقيقة محلي، diff وrollback ناقصان | P0/P1 |
| Bot | كتالوج وأوصاف ومعاينة | لا توجد Slash Commands أو handlers فعلية بعد | P0 |
| الأمان | OAuth state، تشفير، رؤوس حماية، استعلامات parameterized | fallback secrets، CSRF، rate limit في الذاكرة، static root | P0 |
| الاشتراكات | جدول وخطط وسعة معروضة | لا يوجد checkout/webhooks/entitlement موحد أو إنفاذ خادمي | P1 |

## أهم قرارات التنفيذ

1. توحيد Studio حول مصدر بيانات خادمي واحد: مستخدم، Guild، مشروع، Blueprint، إصدار، Bot Profile، Command Set، Change Set، ونتيجة تنفيذ.
2. تحويل كل عملية Discord إلى مراحل: فحص الصلاحيات، معاينة، diff، موافقة، تنفيذ idempotent، نتيجة، ثم rollback أو تعويض عند الفشل الجزئي.
3. فصل ما هو جاهز عن ما هو معاينة أو قيد التطوير في الصفحة الرئيسية والباقات.
4. تقوية الأمان قبل توسيع الاستحواذ، خصوصاً الأسرار وCSRF والتحقق من JSON وعدم تقديم ملفات الخادم بشكل ثابت.
5. جعل الحساب مركز متابعة وتشخيص، وجعل Studio مركز بناء وتنفيذ، وعدم إعادة خلط المشاريع داخل الحساب.

## الأدلة والملاحظات الفنية

- فحص الموقع الحي أعاد `200` للمسارات الرئيسية، و`/api/health` أفاد بأن البوت مهيأ ومتصل في أربعة سيرفرات وقت الفحص.
- مسار OAuth و`authorizedGuild()` يقدمان أساساً حقيقياً، لكن Google لا يملك مساراً واضحاً لربط Discord لاحقاً.
- `discord-bot.js` يستخدم Gateway Guilds فقط ولا يحتوي runtime مكتمل لأوامر Slash أو الإشراف أو الفعاليات.
- تطبيق Change Set ينشئ الموارد الناقصة، لكنه يحتاج diff للأذونات، تحديثاً وحذفاً مضبوطين، idempotency، وrollback.
- تدفق الاشتراك يعرض الخطط والحدود، لكن لا يفرض الحدود في الخادم ولا يقدم دورة دفع أو webhook.
- توجد مخاطر إنتاجية في fallback secrets، وغياب CSRF الصريح، وrate limit داخل الذاكرة، وتقديم جذر المشروع كملفات ثابتة.

## خارطة الميزات والإضافات

تم تجميع 440 ميزة أو إضافة أو تعديل في 22 مجالاً. هذه ليست دعوة لتنفيذها دفعة واحدة؛ بل backlog مصنف يمكن تحويله إلى مراحل. يبدأ التنفيذ بميزات P0 الأمنية والموثوقة، ثم P1 التشغيلية، ثم P2 التحسينات والحوكمة.

## خطة التنفيذ المرحلية

### المرحلة صفر: الثقة والأمان
إلزام أسرار الإنتاج، إضافة CSRF وOrigin checks، إخفاء مصدر الخادم، والتحقق من كل JSON. في هذه المرحلة يجب أيضاً توضيح الميزات غير المنفذة وإصلاح مسارات CTA الأساسية.

### المرحلة الأولى: مصدر حقيقة واحد
ربط Studio بقاعدة البيانات، حفظ المسودات والإصدارات، ربط المشروع بالسيرفر، إنشاء diff، وتوحيد شاشة الحساب مع Studio دون محررات متنافسة أو حفظ محلي غير معلن.

### المرحلة الثانية: ربط Discord موثوق
فحص الصلاحيات الفعلية وترتيب الرتبة، شاشة تثبيت وتشخيص، استيراد بنية السيرفر، Change Set قابل للاستئناف، ومراجعة وrollback.

### المرحلة الثالثة: Bot runtime
تسجيل Slash Commands، handlers، إعدادات لكل Guild، كتالوج أوامر حقيقي، قنوات سجل، مهام مجدولة، moderation policies، ومراقبة صحة البوت.

### المرحلة الرابعة: الاشتراك والإنفاذ
توحيد entitlements، فرض الحدود في الخادم، ثم إضافة checkout وwebhooks والإيصالات والترقية والإلغاء إذا أصبح ذلك ضمن نطاق المنتج.

### المرحلة الخامسة: التوسع والجودة
إكمال الوصول والتعريب، القياس، الدعم، لوحة الإدارة، النسخ الاحتياطي، staging، اختبارات شاملة، ونشر تدريجي.

## المراجع

توضح وثائق Discord أن Bot Token يجب معاملته ككلمة مرور، وأن OAuth2 scopes تحدد ما يسمح به التطبيق، وأن صلاحيات البوت تختلف حسب السيرفر والقناة [1]. كما تشرح وثائق Application Commands حدود الأسماء، وتسجيل أوامر Guild وGlobal، ونطاق `applications.commands`، وصلاحيات الأوامر على مستوى المستخدم والرتبة والقناة [2]. وتؤكد مكتبة السلامة الرسمية أهمية التصميم الآمن، وإجراءات الإشراف التدريجية، وسجل المراجعة، وتمكين المشرفين من أدوات واضحة [3].

[1]: https://docs.discord.com/developers/platform/oauth2-and-permissions "Discord OAuth2 and Permissions"
[2]: https://docs.discord.com/developers/interactions/application-commands "Discord Application Commands"
[3]: https://discord.com/safety-library "Discord Safety Library"
